## Context

The ERP module is a Laravel module under `Modules/ERP`, with table names centralized in
`Modules\ERP\Enums\ERPTables` and physical tables prefixed with `erp_`.

The original milestone documents were written ahead of the current codebase. Before feature
development, implementation plans must be aligned to the actual module shape:

- Domain enums that already exist under `Modules\ERP\Casts` must not be duplicated under
  `Modules\ERP\Enums`.
- E-invoice data classes already live under `Modules\ERP\Data\EInvoice`.
- Eloquent company scoping uses `Modules\ERP\Concerns\BelongsToCompany`.
- ERP factories are not currently present; tests must either create records manually or add
  factories as an explicit task.
- New schema must update `ERPTables` and use `ERPTables::*->value` in migrations, rules, tests,
  and relationships.

## M3.6 - Purchase Invoice Posting Cleanup

M3.6 is not a greenfield implementation. The current code already includes:

- `InvoicePostingService::post()` for sale and purchase directions.
- Purchase invoice document type allocation via `DocumentType::PurchaseInvoice`.
- Purchase journal lines using `purchase_expense`, `vat_input`, and `trade_payable` account roles.
- Purchase 3-way match via `ThreeWayMatchService`.
- `MatchStatus` cases: `Matched`, `Tolerance`, `Forced`, `Unmatched`.
- Per-company 3-way-match settings through `ErpCompanySettings`.

The M3.6 plan must therefore be reduced to verification and cleanup:

- Keep the current `MatchStatus` model; do not introduce `Exceeded`.
- Keep current account role names unless a separate accounting refactor is approved.
- Add missing regression tests only where behavior is not already covered.
- Confirm docs and README use the same role names as code.

## M4 - Policies, Filament Actions, Reporting

M4 must align with Core authorization conventions:

- Core permission names use `{connection}.{table}.{ability}` with table names from the model,
  for example `default.erp_invoices.update`.
- Existing common abilities come from `Modules\Core\Casts\ActionEnum`: `select`, `insert`,
  `update`, `delete`, `restore`, `forceDelete`, `approve`, `publish`, `lock`.
- Custom ERP abilities such as `post`, `unpost`, `force_post`, `close`, `reopen`, `reverse`,
  `unlock`, and `amend` may be seeded explicitly because they represent domain actions rather
  than CRUD/table actions.

Filament actions must reuse existing action classes and services where present. Invoices already
have `Modules\ERP\Filament\Resources\Invoices\Actions\InvoicePostingActions`; new UI work should
extend or reuse that pattern instead of duplicating page-level action logic.

Reporting services remain read-only and must query actual column names:

- `Opportunity` uses `expected_value_doc`, `expected_value_local`, `won_at`, and `lost_at`
  (there are no `amount_doc` / `amount_local` columns on this model).
- `StockLevel` uses `quantity` and `weighted_avg_cost`.

## M6.1 - Bank Reconciliation

Bank reconciliation may add new ERP tables, but every table must be added to `ERPTables`:

- `erp_bank_accounts`
- `erp_bank_statements`
- `erp_bank_statement_lines`

`Payment` already has a nullable `bank_account_id` column, so the plan must decide whether this
becomes a foreign key to `erp_bank_accounts` as part of M6.1. Matching should avoid inventing
an inverse matched-bank-line field on payments; the canonical match link is
`erp_bank_statement_lines.matched_payment_id`.

CSV import remains the first supported import driver. CAMT.053 and MT940 stay out of scope.

## M6.2 - Returns Management

The returns implementation uses dedicated customer and supplier return entities for the primary
workflow. Delivery notes now also have an explicit `direction` column for stock-only inbound or
outbound movements:

- `DeliveryNote::$direction` uses `Modules\ERP\Casts\DeliveryNoteDirection`.
- `erp_delivery_notes.direction` defaults to `outbound`.
- `DeliveryNoteInventoryService::postInventory()` keeps outbound sales-order/COGS behavior and
  supports inbound stock restoration without SO evasion or COGS when an original outbound stock
  movement can provide the returned unit cost.

Return headers remain the source of truth for approval, reason, cancellation, source-document links,
generated DDT links, and credit/debit follow-up links. When a return has a physical movement,
customer returns must generate/link an inbound DDT and supplier returns must generate/link an
outbound DDT. Delivery-note lines carry item, warehouse, quantity, and source links only; prices and
inventory costs stay out of bolle. Credit/debit-note automation remains a follow-up until invoice
source-document and line override modeling is explicit; v1 exposes manual follow-up actions instead.

## M6.3 - E-Invoice Stub And Structure

M6.3 is implemented as a structural e-invoice workflow:

- Bind `EInvoiceProvider` in `ERPServiceProvider`.
- Provide a stub provider that creates a neutral payload and deterministic test responses.
- Persist `EInvoiceSubmission` rows using the existing model and status enum.
- Add minimal Filament actions for submit and status refresh on posted sale invoices.

The current contract is:

```php
public function code(): string;
public function prepare(Invoice $invoice): EInvoicePayload;
public function submit(EInvoicePayload $payload): EInvoiceSubmissionResult;
public function remoteStatus(string $externalId): EInvoiceRemoteStatus;
```

The plan must not require remote-status polling to accept a submission model.

Full FatturaPA XML generation is intentionally outside M6.3 because the module still needs complete
anagraphic, transmitter, recipient, PEC/SDI, fiscal regime, and provider-specific data before it can
promise valid legal XML and production SDI behavior. That work is now tracked by Spec 2 Phase 2C.

## M7.1 - Advanced Pricelists

M7.1 must reflect the existing pricing model:

- `PriceListItem` currently belongs to a price list and a taxonomy, not directly to an item.
- `Item` has an optional `taxonomy_id`.
- New table names must be added to `ERPTables` and prefixed with `erp_`.

The first implementation should resolve prices by taxonomy/list first, then apply party/global
rules. Direct item-specific pricing can be added only if a schema change explicitly introduces an
`item_id` target.

## Testing Conventions

- Tests stay under `Modules/ERP/tests/Feature` or `Modules/ERP/tests/Integration`.
- Use manual model setup unless a task explicitly creates ERP factories.
- Schema assertions use `ERPTables::*->value` and `CoreTables::*->value`.
- Minimal commands:
  - `php artisan test --compact Modules/ERP/tests/Feature/<AreaTest>.php`
  - `vendor/bin/pint --dirty`
